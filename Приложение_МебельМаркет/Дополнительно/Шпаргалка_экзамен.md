## Схема БД (11 таблиц)

| Таблица | Назначение / важные связи |
|---|---|
| `Роли` | Название роли; один-ко-многим с пользователями |
| `Пользователи` | ФИО, уникальный логин, пароль-хеш, роль, необязательная связь с покупателем |
| `Категории` | Справочник категорий товаров |
| `Производители` | Справочник производителей |
| `Поставщики` | Справочник поставщиков |
| `Склады` | Справочник мест хранения |
| `Товары` | Артикул, каталоговые данные, цена, скидка, категория, производитель и поставщик |
| `Остатки` | Составной ключ товар+склад, количество на складе |
| `Покупатели` | Контактные данные покупателя |
| `Заказы` | Покупатель, склад, доставка, код получения, статус |
| `СоставЗаказа` | Товары в заказе, количество и цена на момент покупки |

**Ключи и ограничения:** автоинкрементные первичные ключи; уникальные названия справочников, логин и артикул; составной ключ у остатков и состава заказа; цена и остаток неотрицательные; скидка от 0 до 100; количество в строке заказа больше 0; внешние ключи поддерживают ссылочную целостность.

**Запросы Access:** `Запрос_ОстаткиПоТоварам`, `Запрос_КаталогМебели`, `Запрос_ОстаткиПоСкладам`, `Запрос_Заказы`.

## Краткая логика приложения

1. При старте открывается окно входа. Гость может перейти к каталогу без поиска и сортировки; после входа показывается ФИО и интерфейс роли.
2. Карточка каталога выводит фото или `picture.png`, категорию, наименование, описание, производителя, поставщика, цену, единицу, остатки каждого склада и скидку. Если скидка строго больше 15%, карточка получает фон `#008080`; если остаток равен нулю — серый фон; исходная цена перечёркнута красным, рядом указана цена со скидкой.
3. Авторизованный клиент смотрит товары без поиска/сортировки. Менеджер и администратор фильтруют, сортируют и ищут; менеджер просматривает заказы.
4. Администратор добавляет, изменяет и удаляет товары и заказы. Удаление связанного товара предотвращается ограничениями ссылочной целостности.
5. Дополнительно доступно оформление клиентского заказа: перед записью проверяется остаток выбранного склада, затем транзакционно создаются заказ и строки и уменьшается запас.

## Вопросы, которые могут задать

**Почему 11 таблиц?** Это разумный минимум для отдельных ролей, пользователей, каталога и справочников, многоскладских запасов, покупателей и заказов с несколькими товарами. Объединение этих сущностей создало бы повторы и усложнило изменения.

**Зачем отдельная `СоставЗаказа`?** Один заказ содержит несколько товаров, а один товар встречается во многих заказах. Связующая таблица хранит количество и зафиксированную цену продажи.

**Зачем цена на момент заказа?** Каталожная цена/скидка может поменяться; историческая цена сохраняет сумму ранее оформленного заказа.

**Почему Access и Python?** Access хранит реляционные данные, ограничения и запросы; Python/Tkinter предоставляет интерфейс, ODBC передаёт параметры запросов.

**Как защититься от SQL-инъекции?** Передавать пользовательские значения через `?` и параметры `pyodbc`, а не собирать SQL конкатенацией.

**Как обрабатывается нехватка товара?** В дополнительном сценарии заказа до вставки проверяется количество на выбранном складе; изменения выполняются транзакционно и при ошибке откатываются.

**Какие права у ролей?** Гость и клиент смотрят каталог без поиска/сортировки; менеджер ищет/сортирует товары и просматривает заказы; администратор дополнительно управляет товарами и заказами.

**Пароль в базе — это безопасность?** Дайджест SHA-256 лучше открытого текста, но для учебного примера недостаточно для настоящей защиты. Нужен соль и медленный алгоритм хеширования; Access не следует считать промышленным сервером аутентификации.

**Что проверено?** Python прошёл `py_compile`; демо-XLSX сгенерирован. Проверка Windows GUI, VBA и ODBC через Access не проведена в среде разработки. Перед экзаменом обязательно испытать весь сценарий на компьютере с Access.
